# Sadira Store

E-commerce storefront for **Sadira** — premium modest fashion, Bangladesh.
Next.js (App Router) · TypeScript · Tailwind CSS v4 · Lucide icons.

```bash
npm run dev              # http://localhost:3000
npm run build            # production build (type-checks; does not lint)
npm run lint
npm run catalog:prepare  # rebuild the product catalog from ../Image (+ google-apps-script/InventorySeed.gs)
npm run inventory:seed   # regenerate only google-apps-script/InventorySeed.gs
```

## Data architecture

There is no database. Pages and components talk to `services/` only.

| Data | Source of truth |
| --- | --- |
| Product content (names, descriptions, sizes, colours, designs, slugs) | Google Sheets — Catalog, through `services/catalogService.ts`; local JSON is the seed/unconfigured fallback |
| Product prices | Google Sheets — Catalog |
| Uploaded photos | Private Google Drive folder, served by `/api/catalog/images/<id>` |
| Categories | Local generated catalog — `services/categoryService.ts` → `data/categories.generated.json` |
| **Live inventory** (tracked stock, active/inactive) | **Google Sheets — Products** (via Apps Script) |
| Order history | Google Sheets — Orders / OrderItems |
| Customers | Google Sheets — Customers |
| Inventory audit | Google Sheets — InventoryTransactions |

The catalog's `stock` field is only the **initial seed** for the Products tab
(`google-apps-script/InventorySeed.gs`, generated by `npm run catalog:prepare`) and the
**display fallback** when live inventory isn't configured (local development). It never decides
whether an order is accepted, and the local JSON is never modified at runtime.

When the product source changes, only the service files change; the UI stays the same.
The order + inventory backend (`google-apps-script/Code.gs`) and its setup guide are in
[google-apps-script/README.md](google-apps-script/README.md).

Admin product creation, photo uploads, price/details editing and publishing are implemented.
Follow [the catalog connection guide](google-apps-script/CATALOG-SETUP.md) to connect the
store owner's Google Sheet and Drive. Open `/admin/products` to add/edit products. Live
content changes require no website rebuild. `npm run inventory:seed` also generates
`CatalogSeed.gs`; `setupCatalog()` migrates missing products without overwriting live edits.

Pure, client-safe helpers (prices, discounts, totals) live in `lib/pricing.ts`.
Brand, contact and social details live in `lib/constants.ts`.

## Order flow

The website order is the real order; Google Sheets is the order record; WhatsApp is only a
confirmation channel afterwards.

```
Product page: Add to Cart / Buy Now      (builds a cart line — lib/cart.ts; saves nothing)
      ↓
Cart → Checkout → Place Order
      ↓
Next.js server: validate customer + re-validate items/prices against the catalog
      ↓
Google Apps Script (Code.gs) → writes the order to Google Sheets → returns Order ID (SAD-YYYYMMDD-0001)
      ↓
Order success page → "Send Order Confirmation on WhatsApp" (pre-filled from the SAVED order;
                      the customer presses Send — wa.me links can't send automatically)
```

- An order is created **only** from Checkout — never from the product page.
- WhatsApp is never opened before the order is saved. If saving fails: no success page, no
  Order ID, no WhatsApp; show a retry message.
### Status — Phase 10: real order submission

- `POST /api/orders` (`app/api/orders/route.ts` → `services/orderService.ts`) re-runs the checkout
  validation and rebuilds every item from `productService`: product active, size/colour/design are
  real options, quantity allowed, current price. A changed price returns `PRICE_CHANGED` and the
  bag is updated for review. The delivery charge comes only from server config; subtotal and total
  are computed on the server.
- The server posts to Apps Script (URL + secret server-side only). Apps Script generates the Order
  ID under a lock, writes the Sheet and returns it. A per-attempt `requestId` makes retries safe.
- Only after a confirmed save: the success page (`/order-success`, data via sessionStorage — never
  the URL), the bag or Buy Now item is cleared, and "Send Order Confirmation on WhatsApp" is
  offered (optional; the Sheet's `whatsapp_confirmation` stays Pending).
- **Configuration** (`lib/delivery.ts`, server env — see `.env.example`): delivery charges
  (`DELIVERY_CHARGE_INSIDE_DHAKA`, `DELIVERY_CHARGE_OUTSIDE_DHAKA` — **not supplied yet, so blank**)
  and `APPS_SCRIPT_ORDER_URL` + `APPS_SCRIPT_SECRET`.
  Until both charges **and** the Apps Script settings are present, Place Order explains that
  online ordering isn't available and nothing is saved. Blank charges are never treated as ৳0.
- Customer details are never stored in the browser beyond the current tab's success hand-off.

### Status — Phase 11: inventory & stock sync

- **Apps Script is the only place tracked stock is checked for an order and deducted** — under
  the same script lock as the Order ID and the order write, so two customers can't both buy the
  last unit. Quantities are summed per product across variants. Nothing is written when stock is
  short (`INSUFFICIENT_STOCK`) or the product is inactive (`PRODUCT_UNAVAILABLE`); a failed write
  undoes the whole order, including the stock. Each deduction is logged in InventoryTransactions
  (`SALE`). A retried `requestId` never deducts twice.
- Untracked stock (`track_stock FALSE`, blank) is never treated as 0; those products aren't
  stock-checked. Stock can't go negative.
- `GET /api/inventory` (`services/inventoryService.ts`, cached ~30 s on the server) gives the
  storefront live `productId / trackStock / stock / status / updatedAt`. The browser store
  (`lib/inventoryStore.ts`, `useProductStock()`) shows it on the product page (In Stock / Only X
  left / Out of Stock / Currently Unavailable; purchase buttons disabled at 0), product cards,
  the shop's availability filter, and bag/checkout warnings ("Only 3 are currently available…").
  Display only — Place Order always gets a fresh check in Apps Script.
- A stock rejection at Place Order keeps the bag, the Buy Now item and the form; the bag lines show
  the live stock so the customer can fix quantities and retry.
- Changing an order's status in the Sheet (e.g. Cancelled) does **not** change stock.

## Cart

- State: `components/cart/CartProvider.tsx` (`useCart()`), stored in `localStorage` by
  `lib/cartStore.ts`. The server renders an empty cart; the saved cart appears after hydration.
- Rules in `lib/cart.ts`: a line = product + size + color + design (different variants are
  separate lines; the same variant increases quantity), quantity is capped at real stock (or a UI
  safety limit of 10 when stock isn't tracked), badge = total quantity, `calculateCartSubtotal()`,
  `formatCartOptions()`, and validation of stored data (malformed lines are dropped).
- **Cart prices are display-only.** They live in the browser and can be stale or edited.
  Checkout re-validates product existence and price on the server, and Apps Script checks live
  stock, before the order is saved.
- Quantity limits: live tracked stock when known; otherwise the catalog stock; products without
  catalog stock are limited to 10 per line (UI safety limit, also enforced by the server).
- Buy Now saves one item in `sessionStorage` (`lib/buyNow.ts`) and opens `/checkout?mode=buy-now`;
  it doesn't touch the cart.

## Product catalog

```
../Image/                      original photos + WhatsApp listing screenshots (READ ONLY)
catalog/products.source.json   product info transcribed from the listing screenshots (edit by hand)
        ↓  npm run catalog:prepare
public/catalog/<category>/<id>/  byte-for-byte photo copies: 1.jpeg, 2.jpeg, …
data/products.generated.json     website product data  (do not edit — regenerated)
data/categories.generated.json   website category data (do not edit — regenerated)
```

In `../Image/<Category>/`, each `… details.png` is a listing screenshot for **one product**;
the numbers in its name are that product's photos (`Abaya 4,5 details.png` → `Abaya 4.jpeg`,
`Abaya 5.jpeg`). A details file without numbers covers every photo in its folder.

**Adding or changing a product**

1. Put the photos and the details screenshot in `../Image/<Category>/`.
2. Add or edit its entry in `catalog/products.source.json`: list its `photos` (first = cover)
   and `detailsSource`, and copy only what the listing actually shows. Unknown values are
   `null` (price, stock) or empty (`""`, `[]`).
3. Give a new product the next free ID for its category (`SAD-ABAYA-004`). Never reuse or
   renumber IDs — they stay stable across rebuilds.
4. Run `npm run catalog:prepare`. It validates files, IDs and slugs, and warns about source
   files no product uses. It also regenerates `google-apps-script/InventorySeed.gs`.
5. Give the new product its live inventory row: paste the new `InventorySeed.gs` into the Apps
   Script project and run `setupInventory()` (existing rows are never changed). A catalog `stock`
   is only the starting value — after that, stock is managed in the Sheets Products tab.

Commit `public/catalog/` and the generated JSON: `../Image` isn't available when deploying.

## Categories & navigation

Source folders are read-only; the website uses normalised names (set in `catalog/products.source.json`):
`Borka/` → **Burka** (`burka`), `sunglass/` → **Sunglasses** (`sunglasses`).

**Accessories** is a navigation group only (`/shop?group=accessories`), defined once in
`CATEGORY_GROUPS` (`lib/constants.ts`) as Bag + Bracelet + Sunglasses; use
`getProductsByGroup()` in `productService`. Products keep their own category.

The WhatsApp listing screenshots are internal reference only: they are never copied to
`public/`, and products only keep their source path in `detailsSource`.

## Phase 12 — controlled operational orders (backend foundation)

**Changing Orders.order_status manually does NOT restore stock.** To safely cancel
and restock, use `cancelOrder`; never type Cancelled as a substitute.

Order status is managed through controlled Apps Script actions. The only progression
is Pending → Confirmed → Processing → Shipped → Delivered. Cancellation is a
separate action for Pending, Confirmed, or Processing. No admin panel, customer
status mutation endpoint, authentication system, or customer order lookup is added.

SALE and RESTOCK transactions are stored in InventoryTransactions. OrderStatusHistory
records controlled changes with sequential OSH IDs. Products remains authoritative.

`services/orderOperations.ts` is guarded by `server-only` and prepares future admin
integration; it is not a public route or React Server Action. A future caller must
first authenticate/authorize staff. Its cancellation wrapper invalidates the same
process-local inventory cache used after orders, including uncertain transport outcomes.
Editor-only Apps Script calls cannot reach that in-memory Next.js cache: those calls
use the existing maximum 30-second inventory refresh. Immediate invalidation applies
when the internal Next.js service executes cancellation. See the Apps Script README
for safe editor use and failure recovery. No deployment or environment changes were made.

Run `npm run test:operations` for the local Apps Script simulator and server cache test.

## Phase 13 — Internal Admin Dashboard

Open `/admin/login` to access the internal dashboard. Admin capabilities include orders,
controlled status updates, cancellation/restock, inventory, audited manual stock adjustments,
product availability/tracking, and a searchable customer list. Operational data comes from
Google Sheets through the Next.js server. Public storefront URLs remain unchanged; their
layout now lives under the `(storefront)` route group, separate from the admin interface.

### Configure access

Set these **server-only** environment variables (see `.env.example`):

- `ADMIN_USERNAME`: the internal staff username.
- `ADMIN_PASSWORD`: a strong, unique password of at least 12 characters.
- `ADMIN_SESSION_SECRET`: a random signing secret of at least 32 characters.

Leave them blank to disable sign-in. Never prefix them with NEXT_PUBLIC_, put them in
source code, or commit `.env.local`. Existing `APPS_SCRIPT_ORDER_URL` / `APPS_SCRIPT_SECRET`
remain required for operational data. Deploy the updated Apps Script and run `setup()`;
no database or authentication dependencies have been added.

Authentication uses a server-issued HMAC-signed cookie expiring after eight hours. It is
httpOnly, sameSite=strict, and secure with a `__Host-` name in production. Serve production
admin over HTTPS. Changing any admin credential invalidates existing sessions. Logout
clears the cookie and returns to login; copied cookies remain bearer credentials until
expiry or credential rotation. There is no registration, password recovery, or social login.

Protected page services check the session before every Apps Script read. The protected
layout also checks it. `/api/admin/mutate` and logout check the session independently;
mutations accept POST only and require the browser Origin to match the request Host
(HTTPS in production). A reverse proxy must preserve the public Host header. Cross-origin
and missing-Origin mutation requests are rejected. Admin responses are private/no-store,
with framing blocked. Public `/api/orders` cannot dispatch admin actions.

Login uses one server-process window allowing ten attempts per fifteen minutes with a
generic invalid-credentials message. This small-store temporary limit resets on process
restart and is not shared across replicas; use a shared hosting/edge limiter before scaling
to multiple server instances. Authenticated services are ordinary server-only modules,
not unauthenticated React Server Actions.

### Dashboard and operations

Today uses Asia/Dhaka. Today Orders includes all orders created that day. Today Revenue
is the total value (including delivery and discounts) of today's non-Cancelled orders;
it measures order value, not collected payments. Other status counts cover all orders.
The revenue rule is isolated in `adminGetDashboard` for future Delivered-only changes.
Recent orders are limited to ten. Orders, customers, products, and inventory history are
paginated in Apps Script at 25 records per page; list responses omit private address fields.
The Sheet is scanned server-side for filtering/counting, while only the requested page
reaches the browser. No invented analytics or persistent mock data appear in the app.

Status changes and cancellation require confirmation dialogs and call the Phase 12
functions. Cancellation requires a 3–300 character reason. Success claims stock restoration
only if the backend returns Restored. Pending/Failed restock fences require audited recovery.
Manual Sheet edits still never restock. Product stock edits require a reason and append
ADJUSTMENT_IN / ADJUSTMENT_OUT records; tracking enablement requires an initial count.
Product edits compare the stock, tracking, and status displayed to the operator under the
same script lock, rejecting stale edits. All inventory mutation outcomes invalidate the
existing process-local display cache, including uncertain transport outcomes. Existing
Phase 11 storefront stock checks and rejection rules remain in use.

An interrupted product write or incomplete rollback leaves an INVENTORY_FENCE_* Script
Property. The product is treated as unavailable and further product edits/restocks are
blocked until an operator reconciles Products and InventoryTransactions. See the Apps
Script README for recovery. Committed audit records are append-only; rollback removes
only new uncommitted records.

### Validation

- `npm run test:operations`: Phase 12 regression simulator and cache test.
- `npm run test:admin`: admin reads, dashboard metrics, stock audit/rollback/concurrency,
  tracking, low-stock views, authentication/session expiry, rate limiting, and origin checks.
- `npm run test:admin:browser`: actual Next.js routes and desktop/390px browser workflows
  against an isolated in-memory Apps Script simulator. Requires an available Playwright
  installation/browser; set PLAYWRIGHT_MODULE to the module path if using a bundled runtime.
  Screenshots go to ignored `test-results/`.
- `npx tsc --noEmit`, `npm run lint`, `npm run build`.

The browser harness generates temporary credentials, starts its own local Next.js process
and mock backend, then stops both. It never rewrites `.env.local`, deploys Apps Script,
sends email, or touches a real Sheet. Live Google operations still need deployment validation.

## Phase 14 — Public website structure complete

Added the public footer, About, Contact, FAQ, Size Guide, Return & Exchange, Privacy,
and Terms pages. They share the storefront layout and have meaningful titles, canonical
URLs, and Open Graph metadata using the existing original brand logo. The footer uses
that original logo unchanged in a dark tile, centralized contact/social constants, and
a computed Asia/Dhaka copyright year. Policy and information pages are server-rendered.

Contact and newsletter forms are UI-only. They validate locally and clearly state that
submissions are not sent or saved; no provider, API, email recipient, or new data collection
was added. Submit controls remain disabled until the client event handlers are available.
The size guide lists only exact product-specific catalog size labels, without guessed
measurements. No return periods, refund promises, delivery-time guarantees, founder history,
manufacturing claims, or compliance certifications were invented. Return/exchange questions
are directed to the official contact channels before an item is returned.

Public-site navigation was audited. Unsupported account/wishlist routes and the unsaved
wishlist heart were hidden. The announcement bar no longer advertises a coupon that
checkout cannot apply or promises an unspecified easy-return policy. Header, mobile menu,
footer, category/new-arrival links, search results, product links, policy/contact links and
Continue Shopping all lead to supported routes. Admin navigation and operational workflows
remain separate from the public footer.

Accessibility polish includes a keyboard skip link, one main H1 per public page, logical
shop headings, labelled forms, native keyboard-accessible FAQ accordions, visible focus,
a darker rose accent for text contrast, larger icon/option/quantity/remove touch targets,
and wrapping cart controls on narrow screens. Existing dialog focus trapping, Escape
handling and reduced-motion support remain in use. No new dependencies were introduced.

Run `npm run build` and then `npm run test:public:browser` for the public browser audit.
The harness requires an available Playwright module/browser; set PLAYWRIGHT_MODULE if
using the bundled runtime. It starts an isolated production server with ordering/admin
configuration explicitly blank, preserving `.env.local`, and tests all 13 public routes at
320, 375, 390, 430, 768, 1024, 1280 and 1440 pixels. It also checks populated cart/checkout/
confirmation states, link responses, metadata, labels/headings/alt text, text contrast,
keyboard dialogs, local-only forms, reduced motion, JavaScript-disabled information pages,
and browser exceptions/hydration warnings. Screenshots are saved in ignored `test-results/`,
never in `public/`. No real orders, Google Sheets writes or emails occur during this audit.
